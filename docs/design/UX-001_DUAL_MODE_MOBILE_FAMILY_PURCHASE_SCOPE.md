# UX-001 — کانال‌های کاربری نسیم و تصمیم پرداخت همراه خانواده

- **وضعیت:** Architecture/UX proposal with approved initial payer boundary D-0170; no real order/payment implementation
- **مرجع:** BC-003 (خانواده و سالمندیار)، BC-005 (Authority)، BC-009 (اقتصاد و پرداخت، Draft)، BC-014 و BC-022 (حریم خصوصی، نمایندگی و دسترسی)
- **کانال‌های طراحی پیشنهادی:** اپ موبایل برای سالمند و «همراه خانواده» به‌صورت دو حالت UI در یک اپ؛ اپ موبایل جداگانه سالمندیار؛ پنل وب برای سازمان حمایتگر و اداره نسیم. این مسیر طراحی هنوز جایگزین قرارداد احراز هویت یا تخصیص نقش نیست.
- **تفکیک نقش‌ها:** سالمند، همراه خانواده، سالمندیار حرفه‌ای، سازمان حمایتگر و ادمین هویت/Capability مستقل دارند. فرزند ممکن است عملاً مراقبت کند ولی خودکار «سالمندیار حرفه‌ای» یا «نماینده مجاز پرونده» نیست.
- **قرارداد خرید فاز فعلی:** فرزند با حساب خودش خریدار و پرداخت‌کننده است، سالمند دریافت‌کننده خدمت. **منابع مالی سالمند غیرقابل استفاده در نسخه فعلی**؛ امکان آینده **به تعویق افتاده** نه ممنوع دائمی. هیچ استفاده‌ای از حساب سالمند یا credit وی مجاز/فعال نیست.
- **طراحی Figma:** صفحهٔ همراه خانواده می‌تواند «خرید برای سالمند» را فقط به صورت جریان آینده با برچسب «طرح اولیه / پرداخت متصل نیست» نشان دهد؛ داده‌ها ساختگی و خالی از اطلاعات شخصی باشند. اگر جریان خرید هنوز Contract ندارد، از شبیه‌سازی Checkout قطعی/موفق پرهیز شود.
- **Business OPEN:** کاتالوگ خدمت/کالا، سیاست قیمت‌گذاری، متصدی فروش، عملیات درخواست/سبد/سفارش، قوانین لغو/بازگشت، نوع PSP، مسئول رسیدگی به اختلاف، و سازوکار احراز نسبت/نمایندگی و Consent به‌صورت مستقل تعریف شوند؛ هیچ کدام از D-0170 استنتاج نمی‌شوند.
- **Code/Release:** تغییر مستندات و جهت طراحی؛ بدون backend commerce schema، UI گمراه‌کننده، کد پرداخت یا استقرار Production.
